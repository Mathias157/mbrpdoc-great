# Weather-year cleaning: copy static topology per-year, scale hydro FLH against the base default, and drop DK3 without corrupting wide tables

**Status**: accepted

## Context

`clean_weather_year_inputs.py` (see [0014](0014-weather-year-pipeline-architecture.md)/[0015](0015-weather-year-inc-file-loading.md)) only copied the two `CapDev/{raw,scaled_full_year}` variant folders. Three more problems surfaced when extending it:

1. `to_balmorel/*.inc` (top level, e.g. `GGG_renewable.inc`, `AAA_renewable.inc`, `INVDATASET_renewables.inc`, `GKFX_renewable.inc`, `SUBTECHGROUPKPOT.inc`, ...) was never copied anywhere by this script at all, even though every weather-year scenario needs the new renewable technology/topology additions these represent.
2. `WTRRRFLH_WY.inc`/`WTRRSFLH_WY.inc` (renamed to `WTRRRFLH.inc`/`WTRRSFLH.inc` by `RENAME_FILES`) become the scenario's *entire* override for that symbol - `bb4datainc.inc`'s `$if EXIST .../$if not EXIST ...` is mutually exclusive, so the base default (`base/data/WTRRRFLH.inc`) is never read once an override file exists. Two things follow from actually reading the values: they are scaling factors close to 1.0, not absolute hours (e.g. `WTRRRFLH('AT_A') = 1.0145205048709391;`), and WEATHERYEAR's output covers only a subset of AAA (25 of 48 for WTRRRFLH in the 1982 raw output - confirmed by diffing the two files' AAA keys). Left as a plain overwrite, this would have both used the wrong units *and* zeroed out hydro FLH for the other 23 regions.
3. `config/weatheryear.yml` still lists `DK3_OFF` in `Regions_to_keep.offshore` (a legacy, unused Baltic zone), and WEATHERYEAR labels offshore resource grades as `RG1_OFF`/`RG2_OFF`/`RG3_OFF` in `GDATA_renewable.inc`'s `GDSUBTECHGROUP` column, which doesn't match `SUBTECHGROUPKPOT`'s bare `RG1`/`RG2`/`RG3` domain.

## Decision

- **Copy every top-level `to_balmorel/*.inc` file into both `data_raw/<year>/` and `data_scaled/<year>/`**, unmodified by which variant, via a plain glob rather than a hardcoded list (matches exactly what WEATHERYEAR happens to produce, including future additions). Confirmed these are *not* perfectly identical across years (1982 vs. 1985's `AAA_renewable.inc` differ by a few `AL_VRE-ONS_SP199-HH100_RG*` entries, presumably raw CorRES data gaps for a specific region/turbine/year) - so each year's own output is used rather than picking one canonical year, since each weather-year scenario only needs to be internally self-consistent, not identical to every other year.
- **Rewrite `WTRRRFLH('X')=Y;`/`WTRRSFLH('X')=Y;` into `WTRRRFLH('X')=Y*WTRRRFLH('X');`**, and prepend `$onMulti` + `$include '../../base/data/WTRRRFLH.inc';` + `$offMulti` *before* those assignments (not after). Order matters and was confirmed with an actual `gams` compile, not assumed: a value already assigned before a later `$onMulti`-guarded `$include` is *kept*, not overwritten - so putting the base include first populates every AAA with the base default, and the scaling assignments then multiply only the AAA weather-year actually covers, leaving the rest at the untouched base value. Putting the include after would have made every scaling assignment multiply against zero (the parameter's declared-but-unset default), since `bb4datainc.inc`'s own header declares the parameter empty before either branch of the override runs.
- **Drop `DK3` two different ways depending on file shape**: a plain per-line filter for every file where a region is its own line or row key (SET member lists, PARAMETER assignment lists, `SUBTECHGROUPKPOT.inc`'s row-keyed TABLE), but a proper column-splice for `WND_VAR_T.inc`/`SOLE_VAR_T.inc`, whose `TABLE(SSS,TTT,AAA)` puts AAA as columns. Verified directly against a real `gams` compile: naively dropping the header line (or even just reformatting every row's whitespace while changing nothing else) both corrupt this specific TABLE format and produce `Multiple entry ignored`/`Overlapping row name` errors - only excising the exact original character span of the target column (matched by token index, not text position) from the header and every data row, leaving all other whitespace untouched, survives a real compile.
- **Replace `RG1_OFF`/`RG2_OFF`/`RG3_OFF` with bare `RG1`/`RG2`/`RG3`** everywhere (plain substring replace, safe regardless of file shape since it only rewrites label text, never removes a column/row).

- **Write a `DH.inc` override composing base + the three category adjustments**, since `DH_RESH.inc`/`DH_RESIDENTIAL.inc`/`DH_TERTIARY.inc` (already copied via the static-file glob) are themselves self-multiplicative (`DH(...)=DH(...)*factor;`), same shape as `WTRRRFLH`/`WTRRSFLH`, and nothing was creating this override file at all before now:
  ```
  $include '../../base/data/DH.inc';
  $include '../data/DH_RESH.inc';
  $include '../data/DH_RESIDENTIAL.inc';
  $include '../data/DH_TERTIARY.inc';
  ```
  No `$onMulti` needed here even though `base/data/DH.inc` contains its own `PARAMETER DH(...);` line re-declaring the same symbol `bb4datainc.inc` already declared - confirmed with a real `gams` compile that a *bare* re-declaration (no attached `/ data /` list) is allowed unconditionally; `$onMulti` is only needed when a second statement tries to *load data* into an already-populated symbol (the `WTRRRFLH.inc`/`WTRRSFLH.inc` case above, where the base file's `PARAMETER` line has a `/ list /` attached directly).
- **Prepend `$include '../../base/data/<NAME>.inc';` to the concatenated `DE_VAR_T.inc` and `DH_VAR_T.inc`.** Their sources (`DE_VAR_T_OTHER.inc`/`DE_VAR_T_RESE.inc`, `DH_VAR_T_RESIDENTIAL.inc`/`DH_VAR_T_RESH.inc`/`DH_VAR_T_TERTIARY.inc`) are plain absolute-value assignments (e.g. `DE_VAR_T('DK1','OTHER','S01','T001')=1571.97;`), not scaling factors, but each only covers its own DEUSER/DHUSER categories - every other DEUSER/DHUSER/region/time combination needs the base default. Since these are plain assignments rather than a `$onMulti` data list, ordering here follows a different rule than `WTRRRFLH`/`DH`: confirmed with a `gams` test that a later plain assignment *always* overwrites an earlier one regardless of `$onMulti`, so the base include must run first (providing defaults for everything), with our own category-specific assignments running after to override just their own cells - the reverse order would have let the base's own blanket reassignment (e.g. `DE_VAR_T(...)=DE_VAR_T1(...);`) clobber the weather-year values.
- **Add a permanent Albania onshore-wind fallback** to `WNDFLH.inc`/`WND_VAR_T.inc`: `AL`'s "Existing" onshore category has no turbine-specific profile of its own and intermittently has gaps in the turbine it *would* borrow from (e.g. `SP199-HH100` present in 1985's raw output, missing from 1982's), so `AL_ONS_Existing_RG1`'s profile is unconditionally set equal to `AL_VRE-ONS_SP199-HH150_RG1`'s (a turbine the config keeps enabled) rather than left dependent on whichever turbine happens to have data that year.
- **Stop copying `SUBTECHGROUPKPOT.inc`** - excluded from the static-file glob at the user's request.

## Considered options

- **Remove `DK3_OFF` from `config/weatheryear.yml` instead of filtering it downstream.** Rejected for now - the user scoped this to `clean_weather_year_inputs.py`, and removing it from the config wasn't verified to be side-effect-free for whatever else reads that list.
- **Consolidate the wide-table DK3 removal with the line-based one.** Rejected - proven unsafe by an actual failing `gams` compile (see Decision); the two file shapes need genuinely different logic, not just different regexes.

## Consequences

- `WTRRRFLH.inc`/`WTRRSFLH.inc` still fail to compile for one region today: WEATHERYEAR's raw `WTRRSFLH_WY.inc` output uses the AAA name `LV_Other_DH` for Latvia, but neither `base/data/WTRRRFLH.inc` nor `WTRRSFLH.inc` (which use `LV_RigaR`) declare that member - a domain violation confirmed via `gams` compile, pre-existing in WEATHERYEAR's own naming (not introduced by this change, and not something a plain overwrite would have surfaced either, since GAMS doesn't domain-check the RHS of a bare assignment). Out of scope here; needs a pybalmorel-side fix to WEATHERYEAR's Latvia naming.
- How a weather-year scenario's `data/` folder actually gets these new top-level `.inc` files `$include`d by GAMS is not wired up by this change - `bb4datainc.inc` has no override slot for any of them (confirmed: none of their names appear in it at all). `scripts/Balmorel/base/data/AGKN.inc`/`GDATA_renewable.inc`/`DISCOST_H_renewable.inc`/`INVDATASET_renewables.inc` already exist as separate, apparently-unwired, partially-uncommitted manual edits in the `base/data` submodule (some tracked-and-modified, e.g. `AAA.inc`/`CCCRRRAAA.inc` gaining `PV_Rooftop` entries) - left untouched, not investigated further, and not assumed to be the same effort as this change.

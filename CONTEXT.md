# mbrpdoc-great

Research repo for GREAT energy-system scenarios built on the Balmorel model, including the HPC job pipeline that runs Balmorel on DTU's LSF cluster.

## Language

**Fullyear run**:
A single, monolithic LP solve of one target year's full temporal resolution (all 8760 hours, all seasons at once, `SOLVETYPE=RMIP`). Produces the exact joint-seasonal dispatch and storage result for that year. No internal checkpoints — it is one `SOLVE` statement from start to finish.
_Avoid_: Full run, year run

**Rolling run**:
A season-windowed LP solve of a target year (`RollingSeasons=yes`), run after its fullyear run. Storage state is fixed at each window boundary before moving to the next window. Approximates the fullyear result faster, but doesn't see inter-seasonal storage arbitrage beyond a window.
_Avoid_: Rolling horizon run (fine in prose, but "Rolling run" is the pipeline's own name for the job)

**Investment run**:
The MIP solve that determines capacity investment decisions across all modelled years. Runs before any fullyear/rolling run for a scenario, and its results seed them.

**Wall-time**:
The scheduler's hard job-duration limit — `#BSUB -W` on the LSF cluster, `#SBATCH --time` on the SLURM cluster (see [0002](docs/adr/0002-slurm-migration.md)). Exceeding it gets the job SIGKILLed immediately — no chance for GAMS or CPLEX to write a savepoint, close logs, or exit in a controlled way. Distinct from **RESLIM**, GAMS/CPLEX's own internal solver time limit: most jobs leave it at its shared default (far longer than any job's wall-time, so it never triggers), but the rolling 2050 jobs (both clusters) and the fullyear 2050 jobs' ALLN/VGN warm-start path override it to sit just below that cluster's wall-time, so CPLEX yields control before the scheduler kills the job outright.
_Avoid_: Timeout (ambiguous between the two)

**Graceful stop**:
CPLEX voluntarily ending a solve (by hitting its own RESLIM, set below wall-time) before LSF's wall-time kill fires — so GAMS regains control, writes its savepoint GDX, and exits with a distinguishable status instead of being SIGKILLed mid-solve with nothing recoverable.

**Warm start**:
Resuming a solve from a previous attempt's solution point (levels and basis) instead of starting cold. Only meaningful for simplex-family LP methods — CPLEX's barrier method (the model's current default) does not produce a basis a later solve can resume from.

**Scenario name**:
The single, atomic identifier of one specific `MainResults*.gdx` file — pybalmorel's own `scenario_name`, taken whole (e.g. `EVN_R2050`, or `H2NHPN_WY1990_R2050` for a weather year run), never decomposed into folder/run-type/year parts. One scenario folder can hold several scenario names (different run types, target years, weather years); whatever it encodes, it's handled as one opaque string.
_Avoid_: Result, run (for this level — "Scenario" alone always means the folder)

**Target year**:
A modelled future year (2030/2040/2050) with its own capacity investment decision — what **Fullyear run**/**Rolling run** normally vary across. Distinct from **Weather year**, which varies the *realized weather* a fixed investment decision is dispatched against, not the investment decision itself.

**Weather year**:
One specific historical year (1982–2020) of realized weather-driven time series — VRE production, electricity/heat demand, hydro inflow, heat-pump COP — sourced via `pybalmorel`'s `WEATHERYEAR` module from `data/weatheryear_inputs/` (CorRES/demand/hydro/COP model outputs; a manually-downloaded dataset, e.g. from DTU Data — gitignored, not generated by anything in this repo). Used to test how sensitive a fixed investment decision's operation is to inter-annual weather variability, as opposed to **Target year**, which varies the investment decision itself.

**Weather year run**:
The **Fullyear run**/**Rolling run** pair for one (**Source scenario**, **Weather year**) combination, dispatched against that source scenario's already-fixed investment decision — never a fresh **Investment run**. Lives in its own **WY folder**, submitted via dedicated `jobs/slurm/fullyear_2050_wy.sh`/`rolling_2050_wy.sh` scripts (parallel to the ordinary per-scenario ones, not a branch of them).

**Source scenario**:
The existing, already-invested scenario whose `simex_INV/` a **Weather year run** reuses for its fixed capacities — read directly from `<source scenario>/simex_INV/` at run time, never copied into the WY folder itself.

**WY folder**:
A scenario folder for one **Weather year run**, named `<source scenario>_WY<year>` (e.g. `H2NHPN_WY1990`) and living as a flat sibling of its source scenario directly under `scripts/Balmorel/` — so every existing relative path convention (`../base/data/...`, `../jobs/slurm/...`) keeps working unmodified from inside it.

**weatheryeardata**:
`scripts/Balmorel/weatheryeardata/<variant>/<year>/` — the single, gitignored, shared staging location for one **Weather year**'s cleaned `.inc` files (script B's output, trimmed from the `WEATHERYEAR` module's full per-year output tree). Two variants, both sourced from `WEATHERYEAR`'s `CapDev` output (not `HourlyDispatch` — confirmed unneeded): `data_raw` (from `CapDev/raw`, feeds rolling runs) and `data_scaled` (from `CapDev/scaled_full_year`, feeds fullyear runs) — swapped into a WY folder's own `data/` at the start of each run step, the same way `../base/data/Y_full.inc`/`Y_roll.inc` already are. Shared across every WY folder rather than duplicated per-folder, since it travels with the existing `scripts/Balmorel` sync to HPC.

**Demand category**:
A High/Low label per country per scenario name: High if that country's total demand (electricity + heat + hydrogen, summed in TWh) exceeds the mean total demand across all countries in that same scenario name, Low otherwise.

**VRE category**:
A High Wind / High Solar / High Wind+Solar / Low VRE label per country per scenario name, based on whether that country's wind and/or solar production-to-demand ratio exceeds the mean of that ratio across all countries in the same scenario name.

**Combined category**:
The `{Demand category} Demand / {VRE category}` label per country per scenario name (e.g. "High Demand / High Wind") — the join of Demand category and VRE category, and the level at which cross-scenario comparisons (e.g. cost aggregation) group countries.

**Flexibility option**:
A technology or mechanism whose capacity and/or dispatch can absorb, shift, or smooth demand/supply variability across time or space. Evaluated **per commodity** (electricity, heat, hydrogen — separate plots, not one cross-commodity ranking) against that commodity's system cost, emissions, and security of supply. An option's flex value is signed within a given commodity's plot — see **Commodity-signed flex value** — and the same physical option can appear on more than one commodity's plot (e.g. PtH is negative on the electricity plot, positive on the heat plot). List: electricity/hydrogen transmission, PtH (split into Industrial/Individual/District by `Area`, see [0017](docs/adr/0017-correlation-based-flexibility-provision.md)), electrolysers, Fuel cells, EV charging, V2G, electricity/heat/hydrogen storage, demand response, Nuclear, Thermal, Hydro reservoirs, Peaker (electricity and heat only — no hydrogen backup mechanism exists in this model, see [0010](docs/adr/0010-nuclear-thermal-hydro-reservoirs-and-commodity-aware-peaker.md)), and Other (a residual catch-all for whatever's left unattributed, see **Flexibility provision**). Most options can be plotted on either axis (capacity in GW, or production/throughput in GWh) — but only on their positive/supply-side row; negative/demand-side rows never carry a capacity value, since no capacity symbol exists for "how much of this commodity can this option withdraw." For peaker units, whose modelled nameplate capacity is set heuristically large purely to guarantee feasibility (not a real constraint), the analysis instead uses **effective peaker capacity** — the sum, across regions, of each region's own maximum hourly peaker production — as a stand-in for a meaningful capacity figure. EV charging, V2G, and demand response are exceptions: their capacity is an exogenous model assumption, not an endogenously optimised decision, so only production/use (GWh) is meaningful for them.
_Avoid_: Flexibility source, flexibility technology

**Commodity-signed flex value**:
Within one commodity's flex-option plot, an option's flex value is positive when it injects into that commodity's balance (production, storage discharge) and negative when it withdraws (consumption, storage charging). This is `flex_option_metrics.py`'s own convention (unchanged by [0017](docs/adr/0017-correlation-based-flexibility-provision.md), which only touches `estimate_flexibility_needs.py`'s Daily/Weekly/Annual bars — see **Flexibility provision**). Sourced differently by mechanism: storage reads its charging value from that commodity's own non-dispatchable-demand symbol's `ENDO_INTRASTO`/`ENDO_INTERSTO` category and its discharging value from production data — two separate non-negative quantities combined into one signed pair. PtH/electrolysers read `F_CONS_YCRA(ST)` (electricity consumed) for their negative row and `PRO_YCRAGF(ST)` (commodity produced) for their positive row(s). EV charging/V2G share one already-net GAMS variable (`EL_DEMAND_YCRST` Category=`ENDO_EV`, net G2V-minus-V2G) with no separate gross-charging/gross-discharge symbol to read — unlike storage, this pair is derived, not two independently-reported quantities: the net series is clipped to one sign at raw Region-hour resolution, before any Country/Season/Time aggregation, to approximate each direction (a Region-hour with simultaneous charging and discharging understates whichever side loses the tie). Transmission is the one option this convention leaves unsigned here — `X_FLOW_YCR(ST)`/`XH2_FLOW_YCR(ST)` report gross directional flow (`Country` = the *exporting* country only), used as an unsigned utilisation magnitude for this plot's capacity/use ranking, deliberately out of scope for supply/demand signing; `estimate_flexibility_needs.py`'s own transmission signal is signed differently — see **Flexibility provision**. See [0008](docs/adr/0008-commodity-aware-signed-flexibility-options.md), [0016](docs/adr/0016-split-v2g-into-ev-charging-and-v2g.md).

**Reference scenario**:
The single scenario name (default `base_R2050`) whose Combined category assignment is treated as authoritative and reused for every other scenario in a cross-scenario comparison, instead of recomputing Combined category per scenario. Needed because Combined category is mean-relative and can drift between scenarios as dispatch shifts — see [0004](docs/adr/0004-fixed-category-membership-for-cost-aggregation.md).

**Residual load**:
Hourly non-dispatchable demand minus non-dispatchable supply, per Country/Combined category/system. The signal Daily/Weekly/Annual flexibility need is computed from. Computed per commodity: electricity nets demand against real non-dispatchable supply (see **Non-dispatchable demand**/**Non-dispatchable supply**); heat and hydrogen don't net against anything (see **Non-dispatchable heat demand**/**Non-dispatchable hydrogen demand**) — an asymmetry by design, not an oversight, see [0009](docs/adr/0009-heat-hydrogen-residual-load.md).

**Non-dispatchable demand**:
`EL_DEMAND_YCRST` summed over a fixed set of demand categories — `EXOGENOUS` (inelastic household/industry/datacentre load), `DIST_LOSSES`, `TRANS_LOSSES`, `ENDO_CCS`, `ENDO_BIOMETHANE` (technical/parasitic categories with no flexibility-option home), and the dumb/inflexible share of `ENDO_EV` (from `EV_BEV_dumb.inc`/`EV_PHEV_dumb.inc`). Not user-configurable — every `EL_DEMAND_YCRST` category must land in exactly one place, either here or in exactly one **Flexibility option**'s own signed dispatch, so **Flexibility provision**'s additivity holds; `ENDOGENOUS_ELECT2HEAT`, `ENDO_H2`, and `ENDO_EV`'s flexible/smart share are always excluded here since a flex option always claims them. Always excludes storage charging (`ENDO_INTRASTO`/`ENDO_INTERSTO`), itself a flexibility option. See [0017](docs/adr/0017-correlation-based-flexibility-provision.md).

**Non-dispatchable supply**:
Wind, solar and run-of-river hydro production (fixed, not configurable) — the same "full-certainty" VRE grouping this Balmorel dataset already uses internally (`VRE_CERT_AS.inc`).

**Non-dispatchable heat demand**:
`H_DEMAND_YCRAST` summed over a fixed set of demand categories, `EXOGENOUS` plus any technical/parasitic category with no flexibility-option home (mirroring **Non-dispatchable demand**'s fixed-set principle — the exact heat-side list, analogous to electricity's `DIST_LOSSES`/`ENDO_CCS`, is unverified pending a live read of `H_DEMAND_YCRAST`, see [0017](docs/adr/0017-correlation-based-flexibility-provision.md)), always excluding `ENDO_INTRASTO`/`ENDO_INTERSTO` (heat storage charging — itself a flexibility option). Unlike electricity, **never netted against a non-dispatchable heat supply** — `SOLAR-HEATING` exists but is negligible (~0.2% of this dataset's heat production), so heat residual load is just this demand figure. See [0009](docs/adr/0009-heat-hydrogen-residual-load.md).

**Non-dispatchable hydrogen demand**:
`H2_DEMAND_YCRST` summed the same way as non-dispatchable heat demand — `EXOGENOUS` plus any technical/parasitic category with no flexibility-option home, exact list likewise unverified pending a live read. No non-dispatchable hydrogen supply exists at all in this model — every hydrogen-producing technology (electrolysers, steam reforming) is dispatchable — so hydrogen residual load is also just this demand figure. See [0009](docs/adr/0009-heat-hydrogen-residual-load.md).

**Flexibility need (Daily / Weekly / Annual)**:
Per Geis et al. (2026) — the TWh/a of residual load that must be shifted in time to remove variability at that timescale. Computed as half the summed absolute deviation between one resolution's mean and the next coarser one, chained hourly→daily→weekly→annual so no variability is double-counted across scales. Sign-invariant by construction (built from absolute deviations). See **Flexibility provision** for how a flex option's own per-timescale bars are signed, and [0007](docs/adr/0007-flexibility-option-timescale-decomposition.md).
_Avoid_: Flexibility requirement, storage need (these conflate the need with any one option that could meet it)

**Flexibility provision**:
Per Geis et al. (2026) — how much a flex option's own dispatch reduces (or increases) **Flexibility need** at a given timescale, computed as that option's own deviation curve (period-average at the finer resolution minus the coarser one) multiplied by the *system's* deviation sign at each hour (not the option's own sign), summed and halved. Positive when the option's dispatch aligns with what residual load needs at that hour, negative when it opposes — e.g. an interconnector or battery discharge can go negative in periods where its flow works against system need, regardless of being nominally "supply-side." Exactly additive: every tracked flex option's provision, plus an explicit **Other** catch-all (residual load's own deviation curve minus the sum of all tracked options' deviation curves, computed the same way, not silently omitted), sums to total flexibility need — this is what replaced the older fixed per-option `+1`/`-1` display sign. Transmission's own deviation curve here is net import minus export per country-hour (import = flow into one of that country's regions, export = flow out — both derived from `X_FLOW_YCR(ST)`/`XH2_FLOW_YCR(ST)`, mapped to country via each region's own country), unlike **Commodity-signed flex value**'s unsigned transmission treatment — a country's own cross-border position, not gross link utilisation, is what determines whether transmission helped or hurt that country's own need. See [0017](docs/adr/0017-correlation-based-flexibility-provision.md), [0019](docs/adr/0019-signed-net-transmission-for-flexibility-provision.md).
_Avoid_: Flexibility contribution (ambiguous with flexibility need itself)

# mbrpdoc-great

Research repo for GREAT energy-system scenarios built on the Balmorel model, including the HPC job pipeline that runs Balmorel on DTU's LSF cluster.

## Language

**Fullyear run**:
A single, monolithic LP solve of one target year's full temporal resolution (all 8760 hours, all seasons at once, `SOLVETYPE=RMIP`). Produces the exact joint-seasonal dispatch and storage result for that year. No internal checkpoints — it is one `SOLVE` statement from start to finish.
_Avoid_: Full run, year run

**Rolling run**:
A season-windowed LP solve of a target year (`RollingSeasons=yes`), run after its fullyear run. Storage state is fixed at each window boundary before moving to the next window. Approximates the fullyear result faster, but doesn't see inter-seasonal storage arbitrage beyond a window.
_Avoid_: Rolling horizon run (fine in prose, but "Rolling run" is the pipeline's own name for the job)

**Investment run**:
The MIP solve that determines capacity investment decisions across all modelled years. Runs before any fullyear/rolling run for a scenario, and its results seed them.

**Wall-time**:
The scheduler's hard job-duration limit — `#BSUB -W` on the LSF cluster, `#SBATCH --time` on the SLURM cluster (see [0002](docs/adr/0002-slurm-migration.md)). Exceeding it gets the job SIGKILLed immediately — no chance for GAMS or CPLEX to write a savepoint, close logs, or exit in a controlled way. Distinct from **RESLIM**, GAMS/CPLEX's own internal solver time limit: most jobs leave it at its shared default (far longer than any job's wall-time, so it never triggers), but the rolling 2050 jobs (both clusters) and the fullyear 2050 jobs' ALLN/VGN warm-start path override it to sit just below that cluster's wall-time, so CPLEX yields control before the scheduler kills the job outright.
_Avoid_: Timeout (ambiguous between the two)

**Graceful stop**:
CPLEX voluntarily ending a solve (by hitting its own RESLIM, set below wall-time) before LSF's wall-time kill fires — so GAMS regains control, writes its savepoint GDX, and exits with a distinguishable status instead of being SIGKILLed mid-solve with nothing recoverable.

**Warm start**:
Resuming a solve from a previous attempt's solution point (levels and basis) instead of starting cold. Only meaningful for simplex-family LP methods — CPLEX's barrier method (the model's current default) does not produce a basis a later solve can resume from.

**Scenario name**:
The single, atomic identifier of one specific `MainResults*.gdx` file — pybalmorel's own `scenario_name`, taken whole (e.g. `EVN_R2050`, or `H2NHPN_WY1990_R2050` for a weather year run), never decomposed into folder/run-type/year parts. One scenario folder can hold several scenario names (different run types, target years, weather years); whatever it encodes, it's handled as one opaque string.
_Avoid_: Result, run (for this level — "Scenario" alone always means the folder)

**Target year**:
A modelled future year (2030/2040/2050) with its own capacity investment decision — what **Fullyear run**/**Rolling run** normally vary across. Distinct from **Weather year**, which varies the *realized weather* a fixed investment decision is dispatched against, not the investment decision itself.

**Weather year**:
One specific historical year (1982–2020) of realized weather-driven time series — VRE production, electricity/heat demand, hydro inflow, heat-pump COP — sourced via `pybalmorel`'s `WEATHERYEAR` module from `data/weatheryear_inputs/` (CorRES/demand/hydro/COP model outputs; a manually-downloaded dataset, e.g. from DTU Data — gitignored, not generated by anything in this repo). Used to test how sensitive a fixed investment decision's operation is to inter-annual weather variability, as opposed to **Target year**, which varies the investment decision itself.

**Weather year run**:
The **Fullyear run**/**Rolling run** pair for one (**Source scenario**, **Weather year**) combination, dispatched against that source scenario's already-fixed investment decision — never a fresh **Investment run**. Lives in its own **WY folder**, submitted via dedicated `jobs/slurm/fullyear_2050_wy.sh`/`rolling_2050_wy.sh` scripts (parallel to the ordinary per-scenario ones, not a branch of them).

**Source scenario**:
The existing, already-invested scenario whose `simex_INV/` a **Weather year run** reuses for its fixed capacities — read directly from `<source scenario>/simex_INV/` at run time, never copied into the WY folder itself.

**WY folder**:
A scenario folder for one **Weather year run**, named `<source scenario>_WY<year>` (e.g. `H2NHPN_WY1990`) and living as a flat sibling of its source scenario directly under `scripts/Balmorel/` — so every existing relative path convention (`../base/data/...`, `../jobs/slurm/...`) keeps working unmodified from inside it.

**weatheryeardata**:
`scripts/Balmorel/weatheryeardata/<variant>/<year>/` — the single, gitignored, shared staging location for one **Weather year**'s cleaned `.inc` files (script B's output, trimmed from the `WEATHERYEAR` module's full per-year output tree). Five variants: `data_raw`/`data_scaled` (HourlyDispatch's 8760h/long-term-corrected-aggregated resolution, feeding rolling/fullyear runs respectively — swapped into a WY folder's own `data/` at the start of each run step, the same way `../base/data/Y_full.inc`/`Y_roll.inc` already are) and `capdev_raw`/`capdev_scaled_long_term`/`capdev_scaled_full_year` (CapDev's coarser investment-resolution timesteps — not read by any weather year run today, since those never re-invest, see [0013](docs/adr/0013-weather-year-runs-reuse-fixed-investment.md), but kept rather than discarded for a possible future weather-year-aware investment run). Shared across every WY folder rather than duplicated per-folder, since it travels with the existing `scripts/Balmorel` sync to HPC.

**Demand category**:
A High/Low label per country per scenario name: High if that country's total demand (electricity + heat + hydrogen, summed in TWh) exceeds the mean total demand across all countries in that same scenario name, Low otherwise.

**VRE category**:
A High Wind / High Solar / High Wind+Solar / Low VRE label per country per scenario name, based on whether that country's wind and/or solar production-to-demand ratio exceeds the mean of that ratio across all countries in the same scenario name.

**Combined category**:
The `{Demand category} Demand / {VRE category}` label per country per scenario name (e.g. "High Demand / High Wind") — the join of Demand category and VRE category, and the level at which cross-scenario comparisons (e.g. cost aggregation) group countries.

**Flexibility option**:
A technology or mechanism whose capacity and/or dispatch can absorb, shift, or smooth demand/supply variability across time or space. Evaluated **per commodity** (electricity, heat, hydrogen — separate plots, not one cross-commodity ranking) against that commodity's system cost, emissions, and security of supply. An option's flex value is signed within a given commodity's plot — see **Commodity-signed flex value** — and the same physical option can appear on more than one commodity's plot (e.g. a heat pump is negative on the electricity plot, positive on the heat plot). List: electricity/hydrogen transmission, heat pumps, electrolysers, V2G, electricity/heat/hydrogen storage, demand response, Nuclear, Thermal, Hydro reservoirs, Peaker (electricity and heat only — no hydrogen backup mechanism exists in this model, see [0010](docs/adr/0010-nuclear-thermal-hydro-reservoirs-and-commodity-aware-peaker.md)). Most options can be plotted on either axis (capacity in GW, or production/throughput in GWh) — but only on their positive/supply-side row; negative/demand-side rows never carry a capacity value, since no capacity symbol exists for "how much of this commodity can this option withdraw." For peaker units, whose modelled nameplate capacity is set heuristically large purely to guarantee feasibility (not a real constraint), the analysis instead uses **effective peaker capacity** — the sum, across regions, of each region's own maximum hourly peaker production — as a stand-in for a meaningful capacity figure. V2G and demand response are exceptions: their capacity is an exogenous model assumption, not an endogenously optimised decision, so only production/use (GWh) is meaningful for them.
_Avoid_: Flexibility source, flexibility technology

**Commodity-signed flex value**:
Within one commodity's flex-option plot, an option's flex value is positive when it injects into that commodity's balance (production, storage discharge) and negative when it withdraws (consumption, storage charging). Sourced differently by mechanism: storage reads its charging value from that commodity's own non-dispatchable-demand symbol's `ENDO_INTRASTO`/`ENDO_INTERSTO` category and its discharging value from production data — two separate non-negative quantities combined into one signed pair. Heat pumps/electrolysers read `F_CONS_YCRA(ST)` (electricity consumed) for their negative row and `PRO_YCRAGF(ST)` (commodity produced) for their positive row(s). V2G instead reads one already-net series (`EL_DEMAND_YCRST` Category=`ENDO_EV`) directly, since G2V-minus-V2G is already computed for it. See [0008](docs/adr/0008-commodity-aware-signed-flexibility-options.md).

**Reference scenario**:
The single scenario name (default `base_R2050`) whose Combined category assignment is treated as authoritative and reused for every other scenario in a cross-scenario comparison, instead of recomputing Combined category per scenario. Needed because Combined category is mean-relative and can drift between scenarios as dispatch shifts — see [0004](docs/adr/0004-fixed-category-membership-for-cost-aggregation.md).

**Residual load**:
Hourly non-dispatchable demand minus non-dispatchable supply, per Country/Combined category/system. The signal Daily/Weekly/Annual flexibility need is computed from. Computed per commodity: electricity nets demand against real non-dispatchable supply (see **Non-dispatchable demand**/**Non-dispatchable supply**); heat and hydrogen don't net against anything (see **Non-dispatchable heat demand**/**Non-dispatchable hydrogen demand**) — an asymmetry by design, not an oversight, see [0009](docs/adr/0009-heat-hydrogen-residual-load.md).

**Non-dispatchable demand**:
`EL_DEMAND_YCRST` summed over a configurable set of demand categories via `--demand-categories` (default: `EXOGENOUS` only — inelastic household/industry/agriculture/datacentre load). `ENDOGENOUS_ELECT2HEAT` (heat-pump/resistive-heater electricity use) and `ENDO_EV` (net G2V-minus-V2G EV charging) can be added in, since how inelastic they really are is a modelling judgement call rather than settled fact — see [0006](docs/adr/0006-residual-load-definition-for-flexibility-needs.md). Always excludes storage charging (`ENDO_INTRASTO`/`ENDO_INTERSTO`) and distribution losses (`DIST_LOSSES`), which are dispatchable or technical rather than inelastic.

**Non-dispatchable supply**:
Wind, solar and run-of-river hydro production (fixed, not configurable) — the same "full-certainty" VRE grouping this Balmorel dataset already uses internally (`VRE_CERT_AS.inc`).

**Non-dispatchable heat demand**:
`H_DEMAND_YCRAST` summed over `EXOGENOUS` only by default (mirroring electricity's `--demand-categories` pattern), always excluding `ENDO_INTRASTO`/`ENDO_INTERSTO` (heat storage charging — itself a flexibility option) and technical-loss categories. Unlike electricity, **never netted against a non-dispatchable heat supply** — `SOLAR-HEATING` exists but is negligible (~0.2% of this dataset's heat production), so heat residual load is just this demand figure. See [0009](docs/adr/0009-heat-hydrogen-residual-load.md).

**Non-dispatchable hydrogen demand**:
`H2_DEMAND_YCRST` summed over `EXOGENOUS` only by default, same exclusions as non-dispatchable heat demand. No non-dispatchable hydrogen supply exists at all in this model — every hydrogen-producing technology (electrolysers, steam reforming) is dispatchable — so hydrogen residual load is also just this demand figure. See [0009](docs/adr/0009-heat-hydrogen-residual-load.md).

**Flexibility need (Daily / Weekly / Annual)**:
Per Geis et al. (2026) — the TWh/a of residual load that must be shifted in time to remove variability at that timescale. Computed as half the summed absolute deviation between one resolution's mean and the next coarser one, chained hourly→daily→weekly→annual so no variability is double-counted across scales. Sign-invariant by construction (built from absolute deviations) — but for a flex option's own per-timescale bars (not residual load's), a demand/supply sign is reattached afterward purely for display (negative = demand-side `"consumption"`-kind views, e.g. heat pumps/electrolysers; positive otherwise), so `flexibility_needs.csv`'s `flex_need_twh` is not uniformly ≥0. See [0007](docs/adr/0007-flexibility-option-timescale-decomposition.md)/[0011](docs/adr/0011-signed-flex-need-display-for-demand-side-options.md).
_Avoid_: Flexibility requirement, storage need (these conflate the need with any one option that could meet it)
